# Database migration

## 1. Detect the tool and conventions
- Flyway: `src/main/resources/db/migration/V<version>__<desc>.sql`
- Liquibase: `db/changelog/*.xml|yaml|sql` included from the master changelog
- EF Core: `dotnet ef migrations add <Name>`; Alembic: `alembic revision -m`; Prisma: `prisma migrate dev --name`
Copy the naming and numbering of the latest existing migration. **Never edit a migration that has already run** in a shared environment; add a new one.

## 2. Write it safely
- One logical change per migration.
- **Adding a NOT NULL column to a large table:** add nullable → backfill in batches → add the constraint (separate migrations if the table is big).
- **Renaming/removing a column used by running code:** expand/contract: add new → write both → migrate reads → drop old in a later release.
- Indexes on big tables: Oracle `ONLINE`, SQL Server `WITH (ONLINE = ON)` (edition permitting), PostgreSQL `CREATE INDEX CONCURRENTLY` (outside a transaction).
- Name constraints and indexes explicitly (`pk_payslip`, `fk_payslip_employee`, `ix_payslip_period`); Oracle identifiers ≤ 128 chars (≤ 30 on 12.1 and older).
- Data fixes: deterministic `WHERE`, report affected row count, idempotent where possible.

## 3. Dialect reminders
| Need | Oracle | SQL Server | PostgreSQL |
|---|---|---|---|
| Auto id | `GENERATED BY DEFAULT AS IDENTITY` | `IDENTITY(1,1)` | `GENERATED BY DEFAULT AS IDENTITY` |
| Money | `NUMBER(15,2)` | `DECIMAL(15,2)` | `NUMERIC(15,2)` |
| Text | `VARCHAR2(n CHAR)` | `NVARCHAR(n)` | `VARCHAR(n)` / `TEXT` |
| Bool | `NUMBER(1)` + check | `BIT` | `BOOLEAN` |
| Timestamp | `TIMESTAMP` | `DATETIME2` | `TIMESTAMPTZ` |
Oracle DDL auto-commits: a failed multi-statement migration can leave partial changes. Keep Oracle migrations to one DDL statement where possible.

## 4. Rollback
Provide the undo: Flyway `U<version>__<desc>.sql` (paid Flyway editions only) or a documented manual script; Liquibase `rollback` block; EF `Down()`; Alembic `downgrade()`. State clearly when a step is **not** reversible (dropped data).

## 5. Verify
Run against a local/test DB (Testcontainers or a dev schema), run the app's tests, and update the entity/model to match. Never run migrations against shared or production databases from the agent.
